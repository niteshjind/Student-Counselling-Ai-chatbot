============================================================
1. PROJECT OVERVIEW
============================================================

Student Counselling AI Chatbot is an AI-powered web-based
student counselling assistant designed to answer academic,
course, admission, eligibility, fees, and other university-
related queries.

The system will use Retrieval-Augmented Generation (RAG)
instead of a traditional rule-based or keyword-matching
chatbot.

The chatbot will retrieve relevant information from the
university's knowledge base and provide the retrieved context
to a Large Language Model (LLM). The LLM will generate a
natural-language response based on the retrieved information.

The initial version will run as an independent web application
that simulates the chatbot experience of a university portal.

The architecture must be designed so that the chatbot can
later be embedded into the actual university website as a
floating popup/chat widget after receiving the required
permission and integration access.

============================================================
2. PROBLEM STATEMENT
============================================================

Students frequently need information regarding:

- Available courses
- Course duration
- Eligibility criteria
- Admission process
- Fees
- Academic information
- University-related information
- Counselling-related queries

Traditional FAQ or rule-based chatbots depend on predefined
keywords and fixed responses. Such systems have limited
understanding of natural-language questions and require manual
creation of many question-answer pairs.

The proposed system will use RAG to allow students to ask
questions naturally while keeping responses grounded in the
available university knowledge base.

============================================================
3. PROJECT OBJECTIVES
============================================================

The primary objectives are:

1. Build an AI-powered student counselling chatbot.
2. Implement a Retrieval-Augmented Generation pipeline.
3. Use university-specific data as the chatbot's knowledge base.
4. Support natural-language student queries.
5. Retrieve relevant information before generating answers.
6. Reduce hallucinated or unsupported responses.
7. Provide a modern and responsive chat interface.
8. Display the chatbot as a floating popup/widget.
9. Make the chatbot architecture suitable for future university
   website integration.
10. Provide a maintainable and extensible codebase.
11. Provide source/context information where appropriate.
12. Allow future expansion of the knowledge base.

5. CORE FEATURES
============================================================

5.1 AI CHAT INTERFACE

The system shall provide a web-based conversational interface.

The interface shall include:

- Floating chatbot button
- Popup chat window
- Chat header
- User messages
- AI messages
- Text input
- Send button
- Loading/typing indicator
- Suggested questions
- Clear conversation option

------------------------------------------------------------

5.2 NATURAL LANGUAGE QUERYING

Students shall be able to ask questions using normal language.

Examples:

"What courses are available?"

"What is the eligibility for B.Tech AI and ML?"

"How long is the B.Tech program?"

"What are the admission requirements?"

"What is the fee structure?"

The system should not require exact keywords or predefined
question formats.

------------------------------------------------------------

5.3 RAG-BASED RESPONSE GENERATION

The chatbot shall use Retrieval-Augmented Generation.

The basic flow shall be:

User Question
      |
      v
Query Processing
      |
      v
Embedding Generation
      |
      v
Vector Database Search
      |
      v
Relevant University Information
      |
      v
Context + User Question
      |
      v
Large Language Model
      |
      v
Final Answer

The LLM must use retrieved university information as the
primary source for answering university-related questions.

------------------------------------------------------------

5.4 UNIVERSITY KNOWLEDGE BASE

The initial knowledge base shall use the available university
data provided for the project.

Expected sources include:

- Courses CSV file
- University information document
- Additional approved university documents in future

The system shall support adding additional documents in future.

------------------------------------------------------------

5.5 CSV DATA PROCESSING

The courses CSV file shall be processed before being added to
the vector database.

Processing steps:

CSV
 |
 v
Data Loading
 |
 v
Data Cleaning
 |
 v
Data Validation
 |
 v
Document Conversion
 |
 v
Chunking
 |
 v
Embedding Generation
 |
 v
Vector Database

The system should preserve important course information such
as course name, eligibility, duration, fees, admission details,
and other available fields.

------------------------------------------------------------

5.6 DOCUMENT PROCESSING

The provided university document shall be processed and
converted into searchable text.

Processing steps:

Document
 |
 v
Text Extraction
 |
 v
Cleaning
 |
 v
Chunking
 |
 v
Embedding Generation
 |
 v
Vector Database

The system should support common document formats where
practical, with PDF/DOCX support as an extensible capability.

------------------------------------------------------------

5.7 VECTOR DATABASE

A vector database shall store embeddings of the processed
knowledge-base content.

Initial vector database:

ChromaDB

The vector database shall support semantic similarity search.

The system should retrieve the most relevant chunks for a
student's query.

------------------------------------------------------------

5.8 LARGE LANGUAGE MODEL

The system shall use an LLM for natural-language response
generation.

The initial implementation may use:

Ollama + Llama

The LLM layer should be implemented in a modular way so that
the model can be replaced with another supported LLM/API in
the future without redesigning the complete application.

------------------------------------------------------------

5.9 GROUNDED RESPONSE SYSTEM

The chatbot must follow these principles:

- Prefer retrieved university information.
- Do not invent university-specific information.
- Do not confidently answer unsupported university questions.
- If required information is unavailable, clearly inform the
  student.
- Avoid presenting assumptions as official university facts.

Example fallback response:

"I couldn't find reliable information about this in the
available university knowledge base. Please contact the
appropriate university department or counsellor for the latest
information."

------------------------------------------------------------

5.10 SOURCE INFORMATION

Where technically possible, the chatbot should identify the
document or knowledge-base source used for the response.

Example:

Source:
Course Information

or

Source:
University Admission Document

This feature is intended to improve transparency and trust.

============================================================
6. CHATBOT SCOPE
============================================================

The chatbot's primary scope is university-related information.

IN-SCOPE:

- Courses
- Course details
- Eligibility
- Duration
- Fees
- Admission information
- Academic information available in the knowledge base
- General counselling-related university queries

OUT-OF-SCOPE:

- General internet search
- Weather
- Entertainment
- Personal medical advice
- Financial advice
- Unrelated general questions
- Unsupported university information

For unsupported questions, the chatbot should politely explain
that the requested information is outside its available
knowledge base or scope.

10. PROMPT REQUIREMENTS
============================================================

The system prompt for the LLM should establish that the model
is a university student counselling assistant.

The LLM should:

- Answer clearly.
- Use retrieved context.
- Avoid unsupported claims.
- Avoid hallucinating university information.
- Admit when information is unavailable.
- Maintain a professional and helpful tone.
- Answer in the language/style appropriate to the user's query
  where supported.

The prompt should clearly distinguish between retrieved
knowledge and unsupported information.

============================================================
14. SECURITY REQUIREMENTS
============================================================

The system should:

- Never expose API keys in frontend code.
- Store secrets in environment variables.
- Validate backend requests.
- Restrict administrative functionality.
- Avoid storing unnecessary sensitive user information.
- Implement basic CORS configuration.
- Sanitize uploaded files where applicable.
- Validate file types and sizes.
- Handle errors without exposing internal implementation
  details.

============================================================
15. ERROR HANDLING
============================================================

The system should handle:

- Empty user messages
- Invalid requests
- Backend unavailable
- LLM unavailable
- Vector database unavailable
- Invalid document uploads
- Unsupported file formats
- Retrieval failure
- Missing information
- Timeout errors

The chatbot should show user-friendly error messages.

============================================================
16. PERFORMANCE REQUIREMENTS
============================================================

The chatbot should provide responses within a reasonable
response time under normal local/demo conditions.

The system should:

- Avoid unnecessarily large context windows.
- Retrieve only relevant document chunks.
- Use appropriate chunk sizes.
- Limit the number of retrieved results.
- Avoid repeated unnecessary embedding operations.
- Load the vector database efficiently.

24. IMPORTANT DESIGN PRINCIPLE
============================================================

The project should prioritize correctness and grounded
responses over generating answers to every question.

The chatbot must not pretend to know information that is not
present in the approved knowledge base.

The primary purpose of RAG is to connect the language model
with university-specific information and reduce unsupported
responses.
